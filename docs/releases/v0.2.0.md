# wolf v0.2.0 — local + Gmail mail workflows

`v0.2.0` closes the second feature wave on top of the v0.1 safety
foundation. It adds two complete mail surfaces (local files + Gmail)
plus the audit + traceability plumbing to use them safely.

`v0.2.0` is still a **CLI-only**, **local-first**, **read + draft
only** product. Everything in this release runs with
`--gmail-backend fake` and `network_mode: none` by default.

## TL;DR

- **`mail-*`**: read / search / summarize / draft local `.eml`,
  `.mbox`, and Maildir; thread-aware; UTC date filters;
  `mail-search-summarize` aggregate.
- **`gmail-*`**: read / search / summarize / draft against the
  Gmail REST API via opt-in `--gmail-backend gmail
  --credentials-path PATH`; threaded; direct `--thread-id`
  fetch; audit log covers every API call.
- **`audit-tail`**: re-print `var/audit/audit.jsonl` for
  correlation and operator visibility.
- **No send.** No `gmail.send`, no SMTP, no IMAP. No OAuth
  browser login. No refresh-token flow. The CLI never delivers
  mail.

## Privacy / safety posture

- **Default fake backend, opt-in real Gmail.** The real Gmail
  backend requires an explicit `--credentials-path` to a JSON
  file with `{"access_token": "..."}`. Refresh tokens are
  never refreshed by this CLI. No OAuth browser login.
- **Body bytes wrapped as `UntrustedText(SourceKind.EMAIL)`.**
  Every LLM call routes through the Router with mail-strict
  prompt-injection scanning (warning markers block). Aggregate
  summaries (LLM output feeding back into the LLM) relax to
  warning-allow; critical markers still block.
- **Bounded body output.** `gmail-read`, `gmail-draft`, and
  several mail commands cap body content via
  `--body-preview-bytes`. Full bodies are not embedded in JSON.
- **Audit log covers every Gmail call.** Five new
  `action_kind`s in `var/audit/audit.jsonl`:
  `gmail.search`, `gmail.read`, `gmail.thread`,
  `gmail.summarize`, `gmail.search_summarize`,
  `gmail.create_draft`. Each event carries metadata only
  (provider, counts, ids, lengths). The access token, raw
  mail body, draft body, and Gmail query content are NEVER
  recorded. PR #29 adds `query_fingerprint` (SHA-256 first 12
  hex) so runs can be correlated without storing the query.
- **Fail-closed audit writes.** If `AuditLogger.log` raises
  `OSError`, every `gmail-*` command returns `stage=audit_log`
  with exit 2. For `gmail-draft` this can happen after the
  draft has been created Gmail-side; reconcile by hand.
- **`FakeGmailClient` deliberately exposes no `send` method.**
  `GmailClient` likewise has no send method. The whole module
  path to a `gmail.send` API call does not exist.
- **CI guard hardening.** PR #26 added a workflow step that
  sets a harmless non-AI git identity (`repo-ci`) before the
  `--identity` scan, so the `guard` workflow stays green on
  push and PR events.

## Backwards compatibility

- v0.1 CLI commands (`summarize-email`, `summarize-file`,
  `summarize-dir`, `search-summarize`, `index-files`,
  `search-files`, `check-path`, `robot-preflight`) are
  unchanged.
- Audit log schema is append-only. v0.1 events
  (`llm.*`, `router.*`) coexist with the v0.2 `gmail.*` and
  `mail.*` events.
- No dependency changes. Still stdlib-only.

## Non-goals (unchanged from earlier PRs)

- No mail send (Gmail / SMTP / IMAP).
- No OAuth browser login or refresh-token flow.
- No attachment content download (metadata only).
- No calendar, contacts, push notifications, background sync.
- No GUI / TUI / web UI.
- No new GitHub Actions or attribution policy beyond the
  existing `guard` workflow.

## Upgrading from v0.1.0

1. `git pull` to v0.2.0.
2. Existing v0.1 invocations work without changes.
3. To start using local mail:
   ```sh
   PYTHONPATH=src python3 -m wolf.cli mail-summarize \
       --path ./mail/sample.mbox
   ```
4. To start using Gmail (opt-in, real network):
   1. Obtain an `access_token` per
      [`docs/setup/gmail.md`](../setup/gmail.md).
   2. Save it to `{"access_token": "..."}` outside the repo.
   3. ```sh
      PYTHONPATH=src python3 -m wolf.cli gmail-search \
          --gmail-backend gmail \
          --credentials-path ~/secrets/gmail_token.json \
          --query "from:alice meeting"
      ```
5. Tail the audit log when you want a record:
   ```sh
   PYTHONPATH=src python3 -m wolf.cli audit-tail --output text
   ```

## Known limitations

See [`docs/usage/known_limitations.md`](../usage/known_limitations.md).
The big ones for v0.2:

- Gmail access tokens are not refreshed; expect
  `gmail:*: HTTP 401` when the token expires.
- Audit events store `query_length` + `query_fingerprint` but
  not the query string itself. Reproducing a session purely
  from `audit.jsonl` is not possible — bridge with
  `result.trace` and application logs.
- `gmail-search-summarize` and `gmail-summarize` pay one
  Router call per fetched message. Large `--limit` values are
  expensive.
- Docker default container is `network_mode: none`, so the
  real Gmail backend cannot be exercised inside it without a
  compose override.
