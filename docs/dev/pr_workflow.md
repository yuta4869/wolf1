# GitHub PR workflow and attribution policy

This document operationalizes the policies declared in `CLAUDE.md`:

- `## GitHub PR workflow`
- `## No AI attribution policy`

The intent is to move enforcement from "we trust everyone to read CLAUDE.md"
to "the build fails if someone forgets". This PR introduces the first piece:
a shell script that scans for forbidden attribution markers in commit
messages, staged files, arbitrary files, inline text, and git identity.

## Branch and PR procedure

For every implementation PR from #8 onward:

1. Start clean: `git checkout main && git pull --ff-only origin main`.
2. Branch: `git checkout -b pr-<number>-<short-topic>` (kebab-case).
3. Implement the change.
4. Run the full test suite on the host:
   `PYTHONPATH=src python3 -m unittest discover -s tests -t . -v`.
5. Run the full test suite in Docker:
   `docker compose run --rm wolf`.
6. Only when both pass, run the attribution guard against staged content:
   `scripts/check-no-ai-attribution.sh --staged`.
7. Commit with a `PR #<n>: <imperative subject>` message.
8. Run the guard against the commit:
   `scripts/check-no-ai-attribution.sh --commit HEAD`.
9. Push: `git push -u origin pr-<number>-<topic>`.
10. Create the PR via `gh pr create` (if available) or the compare URL
    `https://github.com/<owner>/<repo>/compare/main...pr-<number>-<topic>`.
11. PR body must follow the format in `CLAUDE.md ## Reporting style`:
    Summary, Files changed, Commands run, Verification, Security / safety
    posture, Risks / limitations, Next recommended step.

Direct push to `main` is forbidden. The one exception was PR #7, which was
committed to `main` before this workflow existed; it will not happen again.

## What the attribution guard catches

`scripts/check-no-ai-attribution.sh` rejects fixed strings such as:

- `Co-Authored-By: Claude` (and lowercase variants)
- `Generated with Claude` / `Generated by Claude`
- `Created by Claude` / `Authored by Claude`
- `Claude Code generated`
- The U+1F916 robot emoji followed by `Generated`

It also rejects git identity values whose name or email contains `claude`
or `anthropic` (case-insensitive). The list lives in
`scripts/check-no-ai-attribution.sh` and can be extended without changing
the calling code.

## Allowlist

Some files legitimately need to mention the forbidden strings to describe
the policy. The guard exempts them when scanned via `--file`:

- `CLAUDE.md`
- `docs/dev/pr_workflow.md`
- `scripts/check-no-ai-attribution.sh`
- `tests/test_no_ai_attribution.py`

The allowlist applies to `--file` and `--staged` modes. It does NOT apply
to `--commit`, `--text`, or `--identity` — those modes are absolute.

## Invoking the guard

```sh
# Check the most recent commit (message + author + committer identity).
scripts/check-no-ai-attribution.sh --commit HEAD

# Check all staged files before committing.
scripts/check-no-ai-attribution.sh --staged

# Check a single file (e.g. a PR body draft).
scripts/check-no-ai-attribution.sh --file /tmp/wolf-pr-9.md

# Check an inline string.
scripts/check-no-ai-attribution.sh --text "$(cat /tmp/draft.md)"

# Check the current git identity (catches AI / bot author misconfig).
scripts/check-no-ai-attribution.sh --identity
```

Exit codes:

- `0` — no forbidden marker found
- `1` — usage / internal error (bad ref, missing file, etc.)
- `2` — forbidden marker found; output identifies which marker and where

## What this does NOT enforce

- Subtle paraphrases that mean the same thing without using the literal
  strings. The guard is a substring check, not an LLM-based classifier.
- Attribution stored in commit GPG signatures, tags, or git notes.
- Identity drift after the commit: if the guard passes at commit time
  but the user later rewrites history, the rewrite has to be re-scanned.
- Code that is *generated by* an AI but contains no attribution string.
  Authorship is a separate concern from attribution markers.

The guard is a tripwire, not a proof of human authorship.

## Opt-in local git hooks (PR #10)

`scripts/install-git-hooks.sh` is an opt-in installer that copies two hooks
into the developer's `.git/hooks/` directory:

- `pre-commit` runs `scripts/check-no-ai-attribution.sh --staged` and
  `--identity`. Any forbidden marker in staged content or any AI / bot
  identity blocks the commit.
- `commit-msg` is given the commit message tempfile by git. It runs
  `--text` on the message contents and `--identity` again. Any forbidden
  marker in the message itself blocks the commit; git preserves the
  message file so the user can edit and retry.

Install:

```sh
scripts/install-git-hooks.sh             # install if no conflict
scripts/install-git-hooks.sh --dry-run   # show what would happen
scripts/install-git-hooks.sh --force     # overwrite existing hooks (backup as .bak)
```

The installer refuses to overwrite an existing non-identical hook unless
`--force` is given. With `--force` it copies the previous file to
`<hook>.bak` first so nothing is silently destroyed. Re-installing the
same byte-identical hook is a no-op.

The hooks themselves are at `scripts/git-hooks/pre-commit` and
`scripts/git-hooks/commit-msg`; they look up the repo root via
`git rev-parse --show-toplevel` and call the attribution guard via
absolute path, so they continue to work after `cd` into subdirectories.
If the guard script is missing or non-executable, the hook fails with a
clear error.

This is opt-in, not enforced by CI. The CI-level enforcement is the
follow-up GitHub Actions PR (see "Future hardening" below).

## CI-level enforcement: GitHub Actions (PR #11, hardened in PR #12)

`.github/workflows/no-attribution.yml` runs the guard on every pull
request and every push. It is the CI guard layer that closes the gap
when a developer has not run `scripts/install-git-hooks.sh` or edits the
PR body in the GitHub web UI after pushing.

Workflow contract:

- Triggers: `pull_request` (types: `opened`, `synchronize`, `reopened`,
  `edited`) and `push`. The `edited` type is what causes a re-scan when
  the PR title or body is changed after the initial push.
- Permissions: `contents: read`, `pull-requests: read`. No write scopes.
- Steps:
  1. `actions/checkout@v4` with `fetch-depth: 2`.
  2. Make the guard executable.
  3. `scripts/check-no-ai-attribution.sh --commit HEAD`.
  4. `scripts/check-no-ai-attribution.sh --identity`.
  5. On `pull_request` only: read `$GITHUB_EVENT_PATH` with Python stdlib,
     extract `pull_request.body`, write it to a temp file, and run
     `scripts/check-no-ai-attribution.sh --file <tempfile>`.
- No `curl`, no `wget`, no `gh` CLI calls, no `${{ secrets.* }}`
  references, no `api.github.com` HTTP requests. The workflow only reads
  the event payload that GitHub already provides on disk.

PR body edits: when a reviewer (or the author) edits the PR body via the
GitHub web UI, GitHub fires a `pull_request` event with `action: edited`.
Because the `edited` type is listed under `pull_request.types`, the
workflow re-runs and the body extraction step receives the new body text.
A `Co-Authored-By` trailer added post-push is therefore caught on the
re-scan rather than slipping past the initial run.

If the PR body is empty, the workflow writes an empty file and the guard
returns exit 0 (no markers). The empty case is logged explicitly so a
reviewer can confirm the scan happened.

The workflow is best-effort: it catches the most common attribution
mistakes but does not replace human PR review. It is also **not** a
substitute for the local hooks (PR #10) — the two layers are
complementary. The local hooks give feedback before the commit lands;
the CI gate is the final review-time enforcement.

### Activation note (default branch)

Until the workflow file is present on the repository's default branch
(`main`), GitHub Actions only runs it on commits in branches where the
file already exists. That means:

- During PRs #11 / #12 themselves, the CI guard runs because the file
  exists on those PR branches.
- For unrelated PRs opened before PR #11 lands on `main`, the workflow
  has no effect.

The first cross-cutting verification happens on the **next PR opened
after PR #11 merges to `main`**. See `docs/dev/ci_first_run.md` for the
verification runbook.

## Future hardening (out of scope for PR #12)

- A regex extension to catch `🤖 (generated|wrote|made)` etc. once we see
  paraphrases in the wild.
- A `--all` mode that scans every tracked file in the repo (not just
  staged), for use during one-off audits of the existing history.
- A `scripts/uninstall-git-hooks.sh` symmetric with the installer, to
  remove the hooks and optionally restore the `.bak` backup.
- Pin `actions/checkout` to a specific commit SHA rather than `@v4`.
